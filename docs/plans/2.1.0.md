## Part 1: a target that already holds files

**The problem.** Nothing tells a site owner that the container or bucket they just connected already holds files under this site's prefix: a bucket reused from a staging copy, from an earlier install, from another site that happened to use the same name. The first sync then mixes this site's library with whatever was there, and a later Disconnect brings all of it back.

**What the user sees.** On Sync & Offloading › Sync, before the first sync (state `configured`, tracking table empty), the plugin lists this site's prefix (`uploads/` for a single site or the main site, `uploads/sites/<id>/` for the others; `DiluxOneOffloadDB::listing_prefix()`). When the listing is empty nothing changes. When it is not, a callout above **Start Sync** says how many objects and how many bytes are there, and offers three ways on:

- **Continue**: sync as usual. Objects with the same key as a local file are overwritten by the local file; the rest stay where they are (and a later Disconnect would bring them back, which the callout says).
- **Empty it first**: deletes every object under this site's prefix, after the owner types the bucket or container name to confirm. Nothing outside the prefix is touched (other sites of a network, other folders). A progress line counts down; a failure stops with the count of what was deleted and what was not.
- **Use another one**: a link to Cloud Provider › Credentials, where the provider is removed and a new one connected.

**Why the prefix and not the whole bucket.** The plugin only ever writes under its prefix, the sites of a network share a bucket on purpose, and the owner decides what else a bucket holds (the maintainer's call, 28 September: no per-object site tag, no attempt to police the rest of the bucket).

**Where.** A new AJAX action `diluxone_offload_inspect_target` (list the prefix through `list_files()`, count and sum, cached in a transient for five minutes so a reload does not list again) and `diluxone_offload_empty_target` (deletes in rounds of the same time budget as the sync, `batch_seconds()`, through `delete_file()`, and reports progress; refuses unless the posted name equals the configured bucket or container and the state is still `configured` with an empty tracking table). Both nonce-checked and `manage_options`. The callout lives in `templates/admin-sync-sync.php`, its script in `assets/js/admin-sync.js`.

**Tests.** Unit: the confirmation rule (name must match, state must be `configured`, table must be empty), the counting. Integration: both actions against the mock provider, including a refused name and a state that moved on. E2E: the callout appears only with objects present, the three ways work, a wrong name is refused. Real suites: seed objects under the prefix and outside it, empty, check that only the prefix went; on a network, that another site's prefix is intact.

## Part 2: the look, on WordPress' own styles

**The problem.** The sync and disconnect screens and their modals are built from inline styles (about 300 `style="…"` attributes across `templates/admin-sync-*.php` and `templates/partials/sync-modal.php`): hand-picked colours, sizes and gradients that do not follow the admin colour scheme, do not match the rest of WordPress and are hard to change.

**What changes.** The modals and big buttons move onto WordPress' own components: `button`, `button-primary`, `button-hero`, `notice` and `notice-*`, the `.card` shape, the admin colour scheme's accent (as the tab strip already does, `Admin::accent_color()`). Inline styles leave the templates for classes in `assets/css/admin.css` (and the per-screen stylesheets); the red "DO NOT CLOSE THIS WINDOW" banner becomes a `notice-error` with the same words. Nothing moves on the page and no flow changes: this is how it looks, not what it does.

**Tests.** E2E: the existing journeys keep passing unchanged (they select by id and text, not by style); the icon-alignment test from 2.0.0 extends to the modals' buttons. A test that no template under `templates/` carries a `style=` attribute beyond an allowed list (the few that are data, such as a progress bar's width). Screenshots regenerated.

## Part 3: speed

**The problem, measured on 27 September.** A sync against Google Cloud Storage started slow and sped up later. The cause is in `SyncManager::process_batch()` (`includes/class-diluxone-offload-sync-manager.php`, around line 460): every round takes pending files ordered by size, largest first (`DiluxOneOffloadDB::get_pending_files()`, `ORDER BY errors ASC, size DESC`), and stops at 12 MB. A library that starts with files of 10 MB or more therefore uploads one file per round, alone, whatever parallelism the user chose; only when the files get small do the parallel uploads fill up.

**What changes.**

- **A round sized by the parallelism.** The byte budget of a round becomes a function of the parallelism chosen (Balanced 5, Fast 20, Intensive 40) instead of a fixed 12 MB, so a round holds enough files to use every slot; the file count stays capped by `batch_size`. The time budget per request (`batch_seconds()`, 8 seconds) does not change: a round already started always finishes, and a request still answers the browser in time for the progress bar.
- **Big and small together.** A round mixes the largest pending files with small ones, so the first seconds are not spent on one video while the slots for thumbnails sit idle.
- **Parts in parallel.** A file above the chunk threshold sends its parts one after another today (Azure blocks, S3 multipart parts, both prepared synchronously before the commit). The parts go through `curl_multi` like whole files, bounded by the same parallelism, with the commit after all of them.
- **Connections reused.** Every round builds new cURL handles on a new multi handle, and pays a TLS handshake per file. A multi handle kept for the whole request, with a shared connection cache (`curl_share_init` with `CURL_LOCK_DATA_CONNECT` where the PHP build has it, plain reuse where it does not), keeps connections open between rounds of the same request.

**Tests.** Unit: the round budget for each parallelism level; the mix of large and small. Integration: a library that starts with large files fills the parallel slots from the first round (count of files per round); a large file's parts all land and the commit assembles them; an aborted part aborts the upload (S3) and leaves no committed blob (Azure). Real suites: the existing journeys, plus one file larger than the chunk threshold on every provider. A timing number is recorded in the pull request, not asserted in CI.

## Part 4: more services

**Presets.** New entries in the Service list of the S3-compatible provider (`includes/providers/class-s3-presets.php`), each with its endpoint pattern, region rule, addressing style, public URL pattern and ACL support taken from the service's own documentation, and a hint line under the list like the existing ones: Hetzner Object Storage, Akamai (Linode) Object Storage, Vultr Object Storage, Scaleway Object Storage, OVHcloud Object Storage, IDrive e2. Each gets its external-service disclosure in `readme.txt` (service, terms and privacy URLs, written out). No account is needed for these: they are tested by the preset table's unit tests and by the form's E2E test that each preset fills in the right endpoint and public URL.

**Backblaze B2 in the real suites.** A fourth real-storage job next to R2 and Google, against a public B2 bucket, with the same fixed-bucket rules (emptied before each journey, the private-bucket step skipped). It needs an account from the maintainer (the free tier, 10 GB, is enough): a public bucket, an application key limited to that bucket, stored as repository secrets and variables like R2's. If the account is not there when the rest of 2.1.0 is ready, this job moves to the next version and nothing else waits for it.

## Part 5: the options around the provider

New settings, on the Settings screen, each off or at a safe default so that updating changes nothing a site did not ask for, except the two noted below (browser caching for new uploads, and the e-mail on failure and recovery), both with a switch to turn them off:

- **Browser caching (`Cache-Control`).** A header stored with every new upload so browsers keep the file instead of asking again: on, one week by default, the value editable, and a switch to turn it off. New uploads only; what is already in the cloud keeps its headers (a line on the screen says so). Azure: `x-ms-blob-cache-control`, part of the signed headers. S3: `Cache-Control` on every PUT and on the multipart create.
- **Folders the initial sync leaves out.** A list of prefixes under `uploads/` (one per line, e.g. `backups/`, `cache/`) that the scan skips, shown under the scan's "Skipped" list with their own reason. `SyncFilter` already supports excluded paths (`includes/DTOs/SyncFilter.php`); `SyncManager::get_sync_filter()` passes an empty list today (around line 186). Files uploaded through the site while offloading is on still go to the cloud: the setting is about the initial sync.
- **An e-mail when the connection fails.** When the third consecutive failure pauses uploads (`ConfigManager::record_connection_failure()`), the site's administrator e-mail gets one message saying what failed and where to look; when the next success clears it (`record_connection_success()`), one more saying it recovered. One message per transition, never one per failure. On by default (the maintainer's call, 28 September), with a switch to turn it off.
- **Tools › Site Health.** A test (`site_status_tests`) that reports the connection health the plugin already keeps (good, or critical with the reason and a link to Status › Health), and a section in the Info tab (`debug_information`) with the provider, the service, the state and the version, never a key.
- **Storage class or access tier.** For new uploads: Azure `Hot` or `Cool` (`x-ms-access-tier`); Amazon S3 `STANDARD` or `STANDARD_IA` and Cloudflare R2 `STANDARD` or `STANDARD_IA` (`x-amz-storage-class`), offered only where the preset says the service supports it. Never an archive class: media must be readable at once. Changeable at any time; files already uploaded keep their class, and the screen says the cheaper classes charge per read and have a minimum storage time.

**Tests.** Unit: each setting's DTO, its default, its clamping; the headers each provider adds (and signs) for each value. Integration: a new upload carries `Cache-Control` and the class or tier (read back with a HEAD); an excluded prefix is skipped and listed with its reason; the e-mail goes out once on the third failure and once on recovery (captured with `pre_wp_mail`); Site Health's test for healthy and unhealthy. E2E: the settings save and survive a reload; Site Health shows the test. Real suites: a new upload's headers read back from the real service on every provider.

## Order, pull requests and the release

One pull request per part, in this order, each merged before the next starts, each with its changelog bullet under `= 2.1.0 =` / `Unreleased.` in `readme.txt`:

1. The roadmap folds 2.1.0 to 2.3.0 into 2.1.0, this plan, and the `= 2.1.0 =` entry with its `Unreleased.` line (this pull request).
2. Part 1, a target that already holds files.
3. Part 3, speed (before the look, so the screenshots are taken once, at the end).
4. Part 4, presets; the B2 job in the same pull request if the account is there, or its own later.
5. Part 5, the options (it may split in two: headers and class; exclusions, e-mail and Site Health).
6. Part 2, the look, with every screenshot regenerated.

Then the maintainer tries the development build; the release pull request removes `Unreleased.` and sets the markers to 2.1.0 (`release-markers.sh prepare`), and the approval publishes.

## Decisions taken here

- The pre-sync check covers this site's prefix only, and emptying deletes only under it; the rest of the bucket is the owner's business.
- The time budget per request stays at 8 seconds; only what a round holds changes.
- Every new option defaults to what the plugin does today, with two exceptions: browser caching, on at one week because it is what a CDN would do and it only affects new uploads; and the e-mail on failure and recovery, on because the alternative is finding out from visitors. Both have a switch to turn them off.
- No archive storage classes, ever.
- The e-mail on failure and recovery is on by default, with a switch to turn it off.
