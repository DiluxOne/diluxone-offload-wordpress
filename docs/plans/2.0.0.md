## Step 1: tests for the settings' effects

Today the suites prove that the four settings are **saved**. Each one gets a test that proves what it **does**. Where the code turns out not to do what the readme says, the fix ships in the same pull request, with the readme line corrected if the behaviour is deliberately narrower.

### Maximum File Size

- Where it acts: `SyncManager::get_sync_filter()` → `SyncFilter::should_sync_file()`, used by the initial sync only. Live uploads through the stream wrapper are not filtered (they are the user's own upload, already accepted by WordPress' `upload_max_filesize`). The readme says "skipped by the initial sync", which is exactly this; no behaviour change.
- Unit (`tests/Unit/DTOs/SyncFilterTest.php`, exists, extend): a file one byte over the limit is rejected, one byte under is accepted; the limit read from `PluginSettings` after `fromPost` clamping (1 MB and 500 MB edges).
- Integration (`tests/Integration/ForwardSyncTest.php`, extend, `FakeCloudClient`): two pending files, 1 MiB and 3 MiB, limit 2 MB → after `process_batch` the small one is uploaded, the big one is marked skipped with the "exceeds maximum file size" reason in `error_message` and counted in the batch summary's `skipped`, and it does not reach the fake client. The summary shape the Sync tab renders is asserted, since that is what the user sees.

### Upload Timeout

- Where it acts today: only the single-PUT upload, the batch curl handle and the block PUTs of the chunked path (`AzureProvider` constructor `upload_timeout`, set from `ConfigManager::get_cloud_client()`). Downloads use 90 s or 300 s, the block commit 300 s or 60 s, listing 60 s, the health probe 30 s, all hard-coded.
- Decision (D1, closed): the setting governs **every transfer of file data** (single PUT, each block or part, the commit, the batch handle, the download handle and `download_file`). Listing, HEAD, health probe and Test Connection keep their fixed 30 s or 60 s; a control request should not wait ten minutes. The Settings help text changes from "for uploads" to "for each transfer request (upload or download)".
- Unit (`tests/Unit/Providers/AzureProviderTest.php`, extend): with `upload_timeout => 45`, the recorded `wp_remote_*` args carry `timeout => 45` for the single PUT and every block PUT, and the batch/download handles carry `CURLOPT_TIMEOUT` 45 (read back with reflection-free `curl_getinfo` is not possible; the handle test captures the options through the existing `ProviderHandlesTest` approach, which inspects the request that reaches `LocalBlobServer`; the timeout itself is asserted by making the server sleep, below).
- Integration, `@group slow` (`tests/Integration/TimeoutTest.php`, new): `LocalBlobServer` gets a `?delay=N` query that sleeps N seconds before answering. Settings saved with timeout 30 (the minimum); a stream-wrapper upload against a `delay=35` endpoint returns a clean failure within 30-33 s, the local file is not written to `uploads/`, `ConfigManager::get_connection_health()` shows `status => failed`, `error_source => upload` and an error code of `timeout`, and the admin banner copy for `timeout` is the one that names the setting. The same for a download through the stream wrapper. Run by `make test-integration` (it adds about 70 s) and always in CI; `make test-integration FAST=1` excludes the group locally.
- Fix that comes with it: the error code passed to `record_connection_failure` on a `WP_Error` timeout is today `exception`; it becomes `timeout` so the banner can say "raise Upload Timeout in Settings". `health_banner_copy` gets that case.

### Force HTTPS for cloud storage URLs

- Where it acts: `CloudStreamWrapper::force_https_on_url()` behind the four filters, only for URLs whose host is `get_cloud_host()`.
- Integration (`tests/Integration/ForceHttpsTest.php`, new, `FakeCloudClient` whose `get_file_url` returns `http://fake.cloud/...`): with the option off, `wp_get_attachment_url` for a synced attachment is `http://fake.cloud/...`; with it on, `https://fake.cloud/...`; `wp_calculate_image_srcset` entries and a stylesheet enqueued from the cloud host are rewritten; a URL on another host is left alone; a site whose `home_url` is https and a provider URL already https are untouched. Requires the `get_cloud_host()` change of [2.7](#27-making-the-core-provider-neutral) (derive the host from `get_file_url`), which is pulled forward into this pull request because without it the fake client has no cloud host and the test cannot exist.
- E2E mock (`tests/E2E/settings-and-provider.spec.ts`, extend): the checkbox round-trips; nothing else, the effect is proven above.

### Debug logging

- Where it acts: `Logger` writes through `error_log` when `WP_DEBUG` is on (errors and warnings) or the toggle is on (informational lines too).
- Unit (`tests/Unit/CloudStorage/LoggerTest.php`, exists, extend): with both off nothing is written at any level; with the toggle on an informational line is written; with `WP_DEBUG` on and the toggle off, an error is written and an informational line is not. The stub's `error_log` capture already exists in `tests/stubs`.
- Integration (`tests/Integration/LoggingTest.php`, new): `ini_set('error_log', <tmp file>)`, toggle off → run a full stream-wrapper upload and a sync batch → the file stays empty; toggle on → the file contains the upload's informational line, and no line contains the access key (the credential-in-log guard the readme promises, asserted here with the real key of the test config).

**Pull request:** `test/settings-effects`, one PR, with the D1 fix if approved. Docs: `readme.txt` Settings FAQ line for the timeout, `docs/testing-and-quality.md` (the new files and the `slow` group).

## Step 2: the S3-compatible provider

One provider, `s3`, that talks the S3 REST API with AWS Signature Version 4, and a **preset** per service that fills in the endpoint, the region rule and the public URL pattern. The user can always overwrite what a preset filled in.

### 2.1 What the user sees

#### Cloud Provider tab (`templates/admin-cloud-provider.php`)

The **Cloud Provider** select gets a second option:

| value | label |
|---|---|
| `azure` | Azure Blob Storage |
| `s3` | S3-compatible storage (Amazon S3, Cloudflare R2, Backblaze B2, DigitalOcean Spaces, Wasabi, Google Cloud Storage, MinIO, …) |

Choosing `s3` shows `#s3-config` (the existing `{provider}-config` id convention, so `showProviderConfig()` keeps working) with these fields, in this order:

| `s3_region` | Region | text | yes, editable | yes | help text per preset: "e.g. `us-east-1`", "`auto`" for R2, "e.g. `us-west-004`" for B2, "e.g. `nyc3`" for Spaces |
| `s3_endpoint` | Endpoint | text (URL) | yes, editable | yes | https; R2 shows the pattern `https://<account id>.r2.cloudflarestorage.com` and the user pastes theirs; Custom starts empty |
| `s3_bucket` | Bucket | text | – | yes | S3 naming rules; validated |
| `s3_access_key_id` | Access Key ID | text | – | yes | |

One `<p>` per preset, all rendered server-side with `hidden` and toggled by JS, so every string is translatable through PHP.

Prefill rule (JS, `assets/js/admin-cloud-provider.js`): when preset, region or bucket change, Endpoint and Public URL are recomputed from the preset's pattern **unless** the user has typed in that field (`data-edited="1"`, set on `input`, cleared when the preset changes). Changing the preset always re-derives both and clears the flag, because a pattern from another service is never right.

**Test Connection** posts `provider: s3` plus the seven fields. The result box is the existing `.connection-result` / `.test-status-message`; the message distinguishes the four failure modes of [2.6](#26-test-connection-and-connection-health). **Save Configuration** stays disabled until a test passes, as today, and the server now enforces it too (2.7, "tested equals saved").

When a provider is configured, the read-only **`#provider-info`** block renders the rows from `ProviderConfig::describe()` ([2.2](#22-configuration-model)) instead of the Azure literals: for S3 that is Service, Bucket, Endpoint, Region, Public URL, Access Key ID (never the secret). "Update Key" becomes **"Update credentials"** and the modal shows, per provider, `#modal-azure-fields` (unchanged) or `#modal-s3-fields`: Access Key ID (prefilled, editable, since a rotation usually gives a new pair) and Secret Access Key (empty). Everything else about the provider (endpoint, bucket, public URL) is immutable in the modal: changing where the media lives is "Remove provider" and a fresh setup, as with Azure today.

**Remove provider** is unchanged.

### 2.2 Configuration model

Stored in `diluxone_offload_config['provider_config']` when `cloud_provider === 's3'`:

| key | example | encrypted |
|---|---|---|
| `preset` | `aws` | no |
| `endpoint` | `https://s3.us-east-1.amazonaws.com` | no |
| `region` | `us-east-1` | no |
| `bucket` | `mug-media` | no |
| `access_key_id` | `AKIA…` | no |
| `secret_access_key` | … | **yes** (`ConfigManager::ENCRYPTED_FIELDS` gains `secret_access_key`) |
| `public_url` | `https://mug-media.s3.us-east-1.amazonaws.com` | no |
| `path_style` | `true`/`false` | no; set by the preset, not shown in the UI |

`endpoint` and `public_url` are stored normalised: scheme and host lower-case, no trailing slash, no query, no fragment. `public_url` may carry a path (`https://cdn.example.com/media`), which is prepended to every key.

**`ProviderConfig` (`includes/DTOs/ProviderConfig.php`)**

- `fromPost()` gets `case 's3'`: maps the seven posted `s3_*` fields to the keys above (`preset` → `path_style` through `S3Presets::pathStyle()`), then `validate_s3_config()`.
- `validate_s3_config(array)`: every field present; `preset` in the known list; `region` matches `/^[a-z0-9-]{1,32}$/`; `bucket` matches `/^[a-z0-9](?:[a-z0-9.-]){1,61}[a-z0-9]$/` and is not an IP; `endpoint` is a URL with scheme `https` (scheme `http` allowed only when `preset === 'custom'`, for MinIO on a LAN or in CI, and the UI shows a warning beside it); `public_url` is an `http`/`https` URL; `access_key_id` 1..128 printable chars; `secret_access_key` non-empty. Messages name the field, never its value, and never the secret.
- `describe(): array<string,string>` (new, both providers): label → value rows for the read-only screens. Azure: Storage account, Container. S3: Service (preset label), Bucket, Endpoint, Region, Public URL, Access Key ID.
- `getStorageAccount()` / `getContainerName()` stay for Azure; S3 gets no per-field getters, the provider reads the array.

**`ConfigManager`**

- `ENCRYPTED_FIELDS`: add `secret_access_key`. Existing Azure configs are untouched; no migration.
- `STATS_TRANSIENTS`: `['azure' => 'diluxone_offload_azure_stats', 's3' => 'diluxone_offload_s3_stats']`; `record_connection_failure()` deletes the transient of the **configured** provider (today it hard-codes the Azure one), `ajax_remove_provider()` deletes both.
- `get_cloud_client()` unchanged: the factory receives `provider_config + upload_timeout`.

**`Admin::save_config()`**: the "this is a provider save" detection becomes `isset($_POST['cloud_provider'])` (today it needs `account_name`); `posted_fields()` whitelist gains the seven `s3_*` names. The save refuses (with the existing error notice) if the "tested equals saved" transient of 2.7 does not match.

| preset | label | endpoint pattern | region | path-style | public URL pattern | notes |
|---|---|---|---|---|---|---|

| `b2` | Backblaze B2 | `https://s3.{region}.backblazeb2.com` | required, e.g. `us-west-004` | yes | `https://{bucket}.s3.{region}.backblazeb2.com` | |
| `spaces` | DigitalOcean Spaces | `https://{region}.digitaloceanspaces.com` | required, e.g. `nyc3` | yes | `https://{bucket}.{region}.digitaloceanspaces.com` | the CDN variant `….cdn.digitaloceanspaces.com` is the user's edit |
| `wasabi` | Wasabi | `https://s3.{region}.wasabisys.com` | required, e.g. `us-east-1` | yes | `https://s3.{region}.wasabisys.com/{bucket}` | |
| `gcs` | Google Cloud Storage (HMAC keys) | `https://storage.googleapis.com` | fixed `auto` (to be confirmed in the real run; `us-east-1` as fallback) | yes | `https://storage.googleapis.com/{bucket}` | interoperability mode; the native provider is step 3 |

`S3Presets` exposes `all()`, `endpoint($preset, $region)`, `publicUrl($preset, $bucket, $region)`, `pathStyle($preset)`, `label($preset)`. The patterns are the single source for the JS prefill (`DiluxOneOffloadProvider.data.s3_presets`).

Virtual-hosted vs path-style only changes how the provider builds the **request** URL for the endpoint (`https://{bucket}.{host}/{key}` vs `https://{host}/{bucket}/{key}`); the public URL is always taken from the field.

### 2.4 The provider class

`includes/providers/class-s3-compatible-provider.php`, `DiluxOneOffload\Providers\S3CompatibleProvider implements CloudStorageClientInterface`, registered in `enhanced-autoloader.php` and `CloudStorageFactory` (`case 's3'`; `get_supported_providers()` gains `'s3' => ['name' => 'S3-compatible storage', 'implemented' => true, 'config_fields' => [the eight keys]]`, which is what `is_configured()` validates against).

Constants: `PART_SIZE = 5242880` (5 MiB, the S3 minimum part size; R2 additionally requires equal-sized parts except the last, which 5 MiB fixed satisfies); `MULTIPART_THRESHOLD = PART_SIZE` for `upload_file()` (the sync engine keeps its own 10 MiB threshold, [2.8](#28-sync-engine)). Memory promise in the readme changes from "4 MiB blocks" to "blocks of at most 5 MiB" (Azure keeps 4 MiB).

Every request: `Host`, `x-amz-date`, `x-amz-content-sha256: UNSIGNED-PAYLOAD`, `Authorization: AWS4-HMAC-SHA256 …` from the signer (2.5). `UNSIGNED-PAYLOAD` is what lets the batch handle stream a file with `CURLOPT_INFILE` without reading it twice; it is accepted by every listed service over TLS. Integrity is verified instead by comparing the **ETag** the service returns with the MD5 the provider computes while it reads (single PUT: `md5_file`, streamed; parts: `md5()` of the part already in memory), plus the byte count as Azure does. A mismatch is a failed upload and the object is deleted (single PUT) or the upload aborted (multipart).

| interface method | S3 request | success | notes |
|---|---|---|---|
| `test_connection()` | see 2.6 | | |
| `upload_file()` | ≤ 5 MiB: `PUT /{key}` with the body; else multipart below | `200` and ETag = MD5 | `Content-Type` from `mime_type_from_path` or the local path, signed |
| multipart (private) | `POST /{key}?uploads` → `PUT /{key}?partNumber=N&uploadId=` × N (5 MiB from `fread`) → `POST /{key}?uploadId=` with the `<CompleteMultipartUpload>` XML | create `200`; each part `200` with ETag = part MD5; complete `200` **and** body `<CompleteMultipartUploadResult>` (S3 can return `200` with `<Error>`) | on any failure: `DELETE /{key}?uploadId=` (AbortMultipartUpload), so no orphan parts are billed; the docs recommend a lifecycle rule for aborted uploads anyway |
| `download_file()` | `GET /{key}` on the endpoint, signed, `stream => true` | `200` | signed, not the public URL, so it works even if the public URL is wrong; partial file removed on failure; error message starts with `HTTP 404` so the stream wrapper's `/\b404\b|not found/i` keeps matching |
| `file_exists()` | `HEAD /{key}` | `200` | `404` → false, anything else → false and logged |
| `get_file_checksum()` | `HEAD` → ETag | ETag without `-` | a multipart ETag (`…-N`) is not an MD5: returns `false` |
| `get_file_info()` | `HEAD` → `Content-Length`, ETag, `Last-Modified` | | `md5` null for multipart objects |
| `delete_file()` | `DELETE /{key}` | `204` | S3 answers `204` for a missing key too; that is success (the Azure `404` = failure case does not exist here) |
| `copy_blob()` | `PUT /{dest}` with `x-amz-copy-source: /{bucket}/{src}` (URL-encoded) | `200` and body `<CopyObjectResult>` | `200` with `<Error>` is a failure; `x-amz-metadata-directive: COPY` |
| `list_files($prefix)` | `GET /?list-type=2&prefix=&continuation-token=` | `200` | loops on `IsTruncated`/`NextContinuationToken`; same 3 attempts, `sleep(2)` and non-retryable set as Azure; `record_connection_failure(code, msg, 'list_files')` on 4xx |
| `get_file_url()` | – | | `public_url . '/' . object_path(key)` |
| `get_provider_name()` | – | | `'s3'` |
| `prepare_batch_upload_handle()` | curl `PUT /{key}`, `CURLOPT_UPLOAD` + `INFILE`, signed headers | `200` | the sync manager checks the status; ETag verification goes through `verify_upload_response()` (2.7) |
| `prepare_chunked_upload_handle()` | create + parts synchronously (`wp_remote_request`, timeout = the setting), returns the curl handle for **Complete** | `200` + result body | mirrors Azure exactly: the handle the sync runs under `curl_multi` is the commit |
| `prepare_download_handle()` | curl `GET /{key}` signed, to `{local}.dlxpart` | `200` | |
| `get_storage_stats()` (2.7) | `list_files(key_prefix)` | | the same classification and transient shape as Azure, transient `diluxone_offload_s3_stats` |
| `describe_error_body()` (2.7) | | | parses `<Error><Code>` and `<Message>`; **drops** `StringToSign`, `CanonicalRequest`, `SignatureProvided` and `AWSAccessKeyId` that S3 puts in a `SignatureDoesNotMatch` body |

Key encoding: `object_path()` encodes each segment per RFC 3986 (`rawurlencode`, then `%2F` never appears because segments are split first); the same string goes into the request URL and the canonical URI. Spaces, accents and `+` are covered by tests, as they are for Azure.

Error messages start with the HTTP status (`HTTP 403: …`) and never contain the bucket, endpoint or key names, because `check_connection_health()` takes the first three digits it finds in the message as the error code (`config-manager.php:852`), and a bucket called `media2024` would otherwise become "error 202". Common codes get a human line: `SignatureDoesNotMatch` → "the Secret Access Key is wrong", `InvalidAccessKeyId` → "the Access Key ID is wrong", `NoSuchBucket` → "the bucket does not exist in this region or endpoint", `RequestTimeTooSkewed` → "the server clock is more than 15 minutes off", `AccessDenied` → "the keys cannot write to this bucket", `PermanentRedirect`/`301` → "wrong region for this bucket".

### 2.5 Signing: AWS Signature Version 4

`includes/providers/class-aws-signature-v4.php`, `DiluxOneOffload\Providers\AwsSignatureV4`, a class of its own so it can be tested against AWS' published test vectors without a provider around it. Pure PHP 7.4, `hash_hmac`/`hash` only.

- `sign(string $method, string $url, array $headers, string $payloadHash = 'UNSIGNED-PAYLOAD', ?int $time = null): array` returns the headers to send (`Authorization`, `x-amz-date`, `x-amz-content-sha256`, `Host`).
- Canonical request per the spec: method, canonical URI (each segment encoded once; the provider passes already-encoded segments and the signer does not double-encode), canonical query (keys and values `rawurlencode`d, sorted, `=` present for empty values, which matters for `?uploads`), canonical headers (lower-case, trimmed, sorted, `host` and every `x-amz-*` always signed, `content-type` signed when present), signed-headers list, payload hash.
- Credential scope `{date}/{region}/s3/aws4_request`; signing key `kSecret → kDate → kRegion → kService → kSigning`.
- Query-string signing (presigned URLs) is **not** implemented; it belongs to the "Signed URLs" item in Later.

Tests: [2.11](#211-tests).

### 2.6 Test Connection and connection health

`test_connection()` proves the two things the plugin needs, in order, and stops at the first failure:

1. **The keys can write.** `PUT {prefix}/.diluxone-offload-probe-{16 random hex}` with a 32-byte body (`prefix` = `CloudStreamWrapper::key_prefix()` of the current site, so a subsite probes its own prefix). Failures map to the human lines of 2.4 (wrong secret, wrong key id, no bucket, wrong region, no write permission, clock skew).
2. **What is written is readable anonymously at the public URL.** `wp_remote_get(public_url/{probe key})` with no auth header, `redirection => 0`, `timeout => 30`. Anything but `200` with the same 32 bytes is: "The keys work, but the object is not readable at the Public URL. Either the bucket does not allow anonymous read of objects, or the Public URL is wrong." This is the S3 counterpart of the Azure "container is private" refusal; without it media would upload fine and every image on the site would be broken.
3. `DELETE` the probe (a failure here is logged, not reported: the object is 32 bytes).

`ConfigManager::check_connection_health()` calls `test_connection()` at most every 5 minutes on the plugin's admin pages, so the probe also runs there: three tiny requests every five minutes, on admin pages only. That is what makes the health banner and the write refusal (3 consecutive failures) react when a bucket is made private or a CDN breaks, so it is kept (D3, closed).

`Admin::ajax_test_connection()` builds the provider from the posted fields for the posted `provider` (today `validate_azure_config` runs unconditionally: it becomes `ProviderConfig::fromPost()` for both). On success it stores the transient `diluxone_offload_connection_test_passed_{user}` with `provider` and a `sha256` of the **complete** provider config, secret included ([2.7](#27-making-the-core-provider-neutral)).

Banner copy (`Admin::health_banner_copy`): the `401/403` case stops mentioning "SAS token / role assignment" and says "the credentials were rejected: the key is wrong, expired, or lacks permission" for both providers; `404` already says "container or bucket".

### 2.7 Making the core provider-neutral

Every place that assumes Azure outside the provider (the full list is the survey behind this plan; the rows below are the ones that change behaviour). These ship first, in a pull request that leaves Azure working identically, so the provider PR is only additive.

| where | today | after |
|---|---|---|
| `CloudStorageClientInterface` | 14 methods | `+ get_storage_stats(bool $force_refresh = false): array`, `+ describe_error_body(string $body): string`, `+ verify_upload_response(int $status, string $body): ?string` (returns an error line or `null`; Azure: `null` on `201`; S3: checks the status, the `<Error>` body on `200` and, when the handle recorded an expected MD5, the ETag). `copy_blob` keeps its name (renaming it buys nothing and touches every test) |
| `SyncManager::upload_chunk_parallel` | `201 \|\| 200`, then `instanceof AzureProvider` for the error text | `$error = $client->verify_upload_response($code, $body)`; the error text comes from the interface |

### 2.8 Sync engine

Unchanged in structure. What the provider must honour, and does:

- `prepare_batch_upload_handle()` for files ≤ 10 MiB, `prepare_chunked_upload_handle()` above (the sync manager's `chunked_threshold`, untouched). For S3 the chunked handle uploads the 5 MiB parts synchronously inside the provider and hands the sync manager the **CompleteMultipartUpload** request to run under `curl_multi`, exactly the shape Azure has with its block list commit. With the 20 MB default maximum this path covers files from 10 to 20 MB.
- `verify_upload_response()` replaces the raw status check ([2.7](#27-making-the-core-provider-neutral)); the handle info array gains `expected_md5` (batch: `md5_file`; chunked: none, the parts were verified one by one) so the provider can check the ETag on the batch path.
- `prepare_download_handle()` writes `{local}.dlxpart`; the sync manager's byte check against `CURLINFO_CONTENT_LENGTH_DOWNLOAD` and the rename are unchanged.
- Reverse sync and remote scan call `list_files(listing_prefix())` and filter with `site_files()`; ListObjectsV2 returns keys the same way (`uploads/sites/2/…`), so multisite needs nothing new.
- Deletes still happen only from the stream wrapper (`unlink`, `rename`), and a `204` on a missing key is a success, which makes `rename()`'s copy-then-delete idempotent on S3.
- The sync manager never calls `record_connection_failure` today; that stays (it is the stream wrapper's and the provider's job) and is one of the things step 1's timeout test pins down.

### 2.9 Security

- The secret is encrypted at rest with the existing `Crypto` (AES-256-GCM, key from the salts), through `ENCRYPTED_FIELDS`. Decrypt failure records `decrypt_failed` as today.
- The secret never leaves the server: the form's password field is empty on render, the "tested" transient holds a hash, the modal never prefills it, `describe()` omits it, `describe_error_body()` strips the signature echo, and no log line contains it (asserted by tests in 2.11 for the provider and for the integration logging test of step 1).
- Requests to the endpoint always use TLS except a Custom preset explicitly typed as `http://`, which the form flags. `wp_remote_*` and curl keep `sslverify`/`CURLOPT_SSL_VERIFYPEER` on; no option to turn it off.
- The probe object name is random and deleted; the anonymous GET carries no credential.
- Every AJAX handler keeps `check_ajax_referer` + `manage_options`; the new fields are sanitized in `fromPost()` (`sanitize_text_field`, `esc_url_raw` for the two URLs) and escaped in the templates; there is no SQL in this step.
- `x-amz-copy-source` and every key are URL-encoded before signing, so a key with `?` or `#` cannot alter the request.
- Nothing is written to `uploads/` on the server, ever; the "no local fallback" rule stands.

### 2.12 Real-storage suites, secrets and where things run

## Decisions taken here

Things this plan settles without asking, because there is one sensible answer:

- **Part size 5 MiB** for S3 (the minimum every listed service accepts and R2's equal-parts rule); Azure keeps 4 MiB; the readme promise becomes "at most 5 MiB".
- **`UNSIGNED-PAYLOAD` with ETag verification** rather than hashing every body twice; integrity is checked by MD5 on every single PUT and every part.
- **Downloads go through the signed endpoint**, not the public URL, so a wrong public URL breaks the site's images (which Test Connection catches) but never the plugin's own reads or Disconnect.
- **One `test_connection()`** for the button, the health check and the reverse-sync start; no lighter variant.
- **Fixed, pre-created buckets** for the AWS and R2 real suites, per-run containers for Azure as today, MinIO bootstrapped from scratch.
- **Path-style** for every preset but AWS.
- **`http://` endpoints** accepted only under the Custom preset, flagged in the form.
- **No presigned URLs** in this step (Later: "Signed URLs").
- **The interface grows** by three methods rather than adding a second `instanceof` chain; `FakeCloudClient` implements them.

## Decisions closed with the maintainer

Taken on 2026-09-25, after the questions each one raised:

- **D1. The timeout setting stays and governs every transfer of file data** (uploads and downloads, blocks or parts and commits). The alternative, removing it and deriving a timeout from the file size, lost the slow-host case and would remove an option already published in 1.0.0. The Settings label becomes "Transfer Timeout" and the help text says what it covers.
- **D2. The probe object has a random name**, `.diluxone-offload-probe-{16 hex}` under the site's prefix, so two administrators testing at once never collide.
- **D3. The health check runs the full probe** (write, anonymous read, delete) every five minutes on the plugin's admin pages. A `HEAD` alone would not notice a bucket made private or a broken public URL, which is exactly what breaks every image on the site.
- **D4. Four pull requests, A/B/C/D as in 2.13.** Each one is squash-merged to `main` and `main` stays at version 1.0.0 the whole time: a feature PR never bumps the version and never creates a tag. The version moves once, in the release-prep PR, and the maintainer pushes the `1.1.0` tag after it merges; that tag is what publishes to wordpress.org.
- **D5. `media` gives way to `s3`** in the readme's five tags.

### 4.2 The four small additions the screens need

- **A1. Timestamps and a speed.** `connected_at` in the provider config, `state_changed_at` next to the plugin state, and `last_transfer_speed_bps` (bytes per second measured over the last sync or disconnect run, saved by the sync manager when a run ends). Three option fields, no table change.
- **A2. Live uploads are recorded.** After a successful upload through the stream wrapper (`upload_temp_file`), a row is written to the tracking table with `synced = 1` (upsert; the sync already does this for its own files). This is what makes "Recent uploads", "last auto-sync" and the counts honest after offloading is on; today a file uploaded while offloading is invisible to the table.
- **A3. Skipped files are recorded.** The scan today counts skipped files (empty, path too long, above the size limit, and the new skip patterns) and logs the reasons; they are not stored, so no screen can list them. A `skipped` reason column (`VARCHAR(32) NULL`) is added to the tracking table through `dbDelta` with a schema-version bump, and the scan writes the row with the reason. The "skipped by size" count and list, and "Skip these paths", read it.
- **A4. Key prefix.** One option that `key_prefix()` and `listing_prefix()` read (`uploads` by default, `uploads/sites/<id>` on subsites, as today), editable in Advanced only while the tracking table is empty; the multisite tests cover both defaults.

## Step 5: Smart Filename inside Offload (the Filenames screen)

"Dilux One - Smart Filename" (today a separate plugin in `mug-website-v2/wp-content/plugins/dilux-one-smart-filename`, ~2 100 lines) renames uploaded files to unique names: hooks `wp_handle_upload_prefilter` and `wp_unique_filename`, keeps the original name in attachment meta, has a rename mode (disabled / selective: pasted images and screenshots / always), a per-type and per-context filter and a small statistics box.

Arguments for integrating it as a **Filenames** screen of Offload:

- Its reason to exist is the cloud: `image.png` pasted twice from the clipboard collides in a bucket and behind a CDN cache, which is why it was written next to Azure Storage in the first place.
- It is small, has no external service, no table and two options; as a screen it is one class, one template and one settings group.
- One plugin to install, review, translate and publish on wordpress.org instead of two; one review on wordpress.org instead of two.

Arguments against:

- It is useful **without** Offload (any site that pastes screenshots), and inside Offload it would only be available to sites that offload. Its users would have to install a cloud plugin to rename files.
- Offload's readme, review surface and risk grow for something unrelated to storage; the wordpress.org reviewers read every hook.
- Two plugins that both ship the shared "DiluxOne" menu class would become one, but that class is already gone from Offload (standalone menu).

Recommendation: **integrate it, as an optional screen that is off by default**, with the rename hooks registered only when the mode is not "disabled", so a site that only wants renaming can still install Offload without configuring a provider (Offload does nothing until a provider is configured, and the Filenames screen does not need one). The separate plugin stays published for whoever has it and its readme points to Offload; no automatic migration, the two options are copied by hand in the new screen (it is two radio buttons and a few checkboxes). If the maintainer prefers to keep it separate, nothing in this plan changes and the Filenames row of the candidate menu disappears.

Approved on 2026-09-25 as the **Filenames** screen: Renaming (mode, upload contexts, filename options), File types, Statistics, with the plugin's options exactly as they are today and off by default.
